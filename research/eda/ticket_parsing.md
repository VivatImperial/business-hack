# Ticket Parsing Spec (KISS)

Один практический документ под исходный scope:  
из тикета извлекать только:

1. **Исходный запрос**  
2. **Как решили**

## 1) Что такое тикет в этой БД

Тикет — это не одно поле. Это набор источников:

- `Task` — карточка заявки (`Name`, `Description`, даты, статусы, тип, сервис).
- `TaskExpenses` — журнал работ (шаги, комментарии, минуты, дата).
- `TaskFieldValues` (+ `TaskTypeField`) — структурированные поля формы.

Минимально полезная модель:

- **Request part** = `Task.Name` + `Task.Description` + релевантные custom fields.
- **Resolution part** = `TaskExpenses.Comments` (приоритетно) + очищенный `Task.Comment` (fallback).

## 2) Что реально лежит внутри (по факту данных)

- Всего тикетов: `104395`.
- Непустой `Task.Comment`: `91438`.
- В `Task.Comment` boilerplate автозакрытия: `81275` (почти `89%` непустых comment).

Практический вывод:

- `Task.Comment` **нельзя** считать решением по умолчанию.
- Главный источник “как решили” — `TaskExpenses.Comments`.
- Custom-поля обязательны для контекста (особенно тип `Контроль качества`).

## 3) KISS-правило извлечения “Исходный запрос”

Собираем `request_text` строго по приоритету:

1. `Task.Name` (всегда)
2. `Task.Description` (если не пусто)
3. Релевантные custom fields (если есть):
   - `Тип обращения`
   - `Наименование продукции`
   - `Торговая марка`
   - `Производственная площадка`
   - `Смена`
   - `Контакты`
   - `Обращение от`

Что выкидываем:

- пустые/`...`/служебные значения,
- дубли `combobox` vs `value` (оставляем более человекочитаемое).

## 4) KISS-правило извлечения “Как решили”

Собираем `resolution_text` по приоритету:

1. Все содержательные `TaskExpenses.Comments` в хронологическом порядке.
2. Если worklog пустой -> берем `Task.Comment`, **если** это не автошаблон.
3. Если и там пусто -> `resolution_text = null`.

Фильтр шума для `Task.Comment`:

- исключать строки с паттерном  
  `автоматически переведена в статус ... по истечении ...`

## 5) Канонический выход парсера (минимум)

```json
{
  "ticket_id": 0,
  "request_text": "...",
  "resolution_text": "...",
  "resolution_source": "worklog|comment|none",
  "meta": {
    "service": "...",
    "task_type": "...",
    "status": "...",
    "created_at": "...",
    "closed_at": "..."
  }
}
```

Это уже достаточно для QA-RAG индекса.

## 6) Примеры “как это выглядит”

### Пример A: тикет с нормальным решением в worklog

- `Task.Id = 31929`
- Запрос:
  - `Name`: "Ошибка при увольнении"
  - `Description`: "Не получается провести увольнение..."
- Решение:
  - `TaskExpenses.Comments`: "анализ ошибки, изменение начисления"

Итог:

- `request_text` -> из `Name + Description`
- `resolution_text` -> из `TaskExpenses.Comments`
- `resolution_source = worklog`

### Пример B: тикет, где Comment бесполезен

- `Task.Id = 38665`
- `Comment`: автошаблон автозакрытия (шум)
- Есть rich custom fields (`Тип брака`, `Результат`, `ТМ`, `Смена` ...)
- Worklog отсутствует

Итог:

- `request_text` -> из `Name + Description + custom fields`
- `resolution_text = null`
- `resolution_source = none`

## 7) Алгоритм парсинга в 7 шагов

1. Забрать `Task`.
2. Забрать `TaskExpenses` по `TaskId`, отсортировать по дате.
3. Забрать `TaskFieldValues` + названия полей из `TaskTypeField`.
4. Нормализовать текст (trim, схлопнуть пробелы, убрать мусор `...`).
5. Собрать `request_text`.
6. Собрать `resolution_text` по приоритету источников.
7. Вернуть канонический JSON.

## 8) Что важно не делать

- Не пытаться “выдумывать” решение, если его нет в данных.
- Не тащить в `resolution_text` автостатусы и системные шаблоны.
- Не усложнять схемы: для первого релиза достаточно 5 полей и `meta`.
